# Page Object generator

> New to TypeScript? See [docs/typescript-for-beginners.md](typescript-for-beginners.md) if the
> generated code on this page looks unfamiliar.

`pw-sapui5 generate` launches a real browser, navigates to a running SAPUI5 app, waits for it to
settle, reads its live control tree, and writes a starter `Ui5Page` subclass - one getter per
control it finds. It's meant to save you the tedium of hand-typing every locator when you're
starting on a new app, **not** to produce a finished, ready-to-commit Page Object.

## Usage

After installing the package (or from a clone of this repo, after `npm run build`):

```bash
npx pw-sapui5 generate --url https://your-app.example.com/ --output pages/HomePage.ts --class-name HomePage
```

### Options

| Flag                      | Default              | Description                                                                                                         |
| ------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `-u, --url <url>`         | _(required)_         | URL of the SAPUI5 app to inspect                                                                                    |
| `-o, --output <path>`     | `./GeneratedPage.ts` | Where to write the generated file                                                                                   |
| `-c, --class-name <name>` | `GeneratedPage`      | Name of the generated class                                                                                         |
| `--headed`                | off                  | Run the inspection browser headed (useful to watch it load, or if the app needs a login you perform manually first) |
| `--timeout <ms>`          | `30000`              | Navigation / ready timeout                                                                                          |

## What it does, step by step

1. Launches Chromium.
2. Installs the bridge script and navigates to `--url`.
3. Waits for the SAPUI5 runtime to bootstrap and the app to settle (same auto-wait as
   `waitForUi5Core` + `waitForUi5` - see [docs/auto-wait.md](auto-wait.md)).
4. Reads every control currently rendered in the DOM (non-visual objects like `CustomData` and
   pure layout containers like `sap.m.Page`/`sap.m.VBox` are filtered out - they're rarely useful
   as named locators).
5. Generates one `get <name>()` per remaining control, named from its id (or its control type if
   it has no meaningful id), returning `this.id('<idPart>')`.
6. Writes the result to `--output`.

## Example output

```ts
import type { Page } from '@playwright/test';
import { Ui5Page } from 'playwright-sapui5';

/**
 * Auto-generated by `pw-sapui5 generate`. Review before committing:
 * member names are derived from control ids and may not be meaningful.
 */
export class CartPage extends Ui5Page {
  constructor(page: Page) {
    super(page);
  }

  // sap.m.SearchField
  get searchField() {
    return this.id('searchField');
  }

  // sap.m.List text="Categories"
  get categoryList() {
    return this.id('categoryList');
  }

  // sap.m.StandardListItem text="Laptops"
  get categoryList7() {
    return this.id('categoryList-7');
  }

  // ...
}
```

The `//` comment above each getter shows the control's type and any text/title/value/label it
exposes, to help you figure out what each generated member actually is.

## Review before committing - this is a starting point

The generator is deliberately dumb about naming: a control with an explicit id (like
`searchField` above) gets a clean, meaningful getter name. A control SAPUI5 auto-generated an id
for gets a name like `categoryList7` - accurate, but not very readable. Go through the output and:

- **Rename members** to something meaningful (`get laptopsCategory()` instead of `get
categoryList7()`).
- **Delete members you don't need.** A real app can easily have hundreds of controls; the
  generator includes everything it finds that isn't filtered out by default, so trim it down to
  what your tests actually use.
- **Prefer `text`/`controlType` locators over generated raw ids where the id itself looks
  auto-generated** (starts with `__`, or otherwise doesn't look like something a developer
  assigned on purpose) - see the note on this in
  [docs/core-concepts.md](core-concepts.md#why-this-matters-for-locator-design). The generator
  always emits `this.id(...)`, since it's the one strategy guaranteed to be available for
  whatever it found - upgrading a specific getter to a more resilient strategy is a manual step.
- **Combine repeated list-item getters into a parameterized method** (see
  [docs/page-objects.md](page-objects.md#parameterized-locators-for-repeated-elements)) instead
  of keeping dozens of near-identical getters for each row a bound list happened to render at
  inspection time.

## Limitations

- Only controls **currently rendered in the DOM** at inspection time are included. A `sap.m.List`
  with `growing` enabled, for example, only renders items within its initial viewport - items
  further down won't appear until you scroll (or increase the growing threshold) before running
  the generator. If you need a control that only appears after some interaction (a dialog,
  a different route), navigate/interact manually with `--headed` open, and adjust `--url` or the
  generated file afterward.
- If your app requires authentication, use `--headed` and log in manually in the opened browser
  window before... actually, since the CLI navigates and immediately starts waiting, you'll need
  to either point `--url` at an already-authenticated deep link, or extend the CLI's script (see
  [`src/generator/cli.ts`](../src/generator/cli.ts)) to pause for manual login - it's a small,
  readable file, and a reasonable starting point to adapt for your own auth flow.
- The generator has no notion of "this is a duplicate of that other control" - a bound list with
  100 rows produces 100 getters. This is intentional (better to show you everything than silently
  hide it), but expect to prune large lists yourself.
