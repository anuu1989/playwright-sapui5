# Ui5I18n (the app's own translated texts)

> New to TypeScript? See [docs/typescript-for-beginners.md](typescript-for-beginners.md) if the
> code on this page looks unfamiliar.

`Ui5I18n` reads text out of the app's **own** i18n `ResourceBundle` - the exact string the app
itself renders, in whatever language it's currently running in. See
[`examples/tests/i18n-and-model.spec.ts`](../examples/tests/i18n-and-model.spec.ts) for complete,
real, passing examples.

## Why hardcoded strings are a bug waiting to happen

This looks fine:

```ts
await expect(page.getByText('Product Catalog')).toBeVisible();
```

But `'Product Catalog'` isn't the app's text - it's _one language's rendering_ of the key
`homeTitle`, frozen into the test at the moment it was written. It silently stops matching when:

- the suite runs against a system in another language (the single most common cause - SAP
  landscapes are multi-language almost by definition),
- a translation lands, or someone fixes a typo in the English bundle,
- the app switches which key a control binds to.

None of those are bugs in the app, but all of them break the test. Look the key up instead and the
test asserts against _the same source of truth the app renders from_:

```ts
const homeTitle = await Ui5I18n.getText(page, 'homeTitle');
await expect(
  await ui5(page).text(homeTitle, { controlType: 'sap.m.Title' }).resolve(),
).toBeVisible();
```

Now it passes in every locale, and fails for the one reason it should: the app showing genuinely
wrong text.

## Reading a text

```ts
const text = await Ui5I18n.getText(page, 'homeTitle');
```

Searches every component's `i18n` model, resolving the resource bundle first (SAPUI5 returns a
**Promise** from `getResourceBundle()` whenever the bundle loads asynchronously, which real apps
commonly do - handled for you).

### Placeholders

```ts
// bundle: priceKey = "Price ({0} - {1} EUR)"
await Ui5I18n.getText(page, 'priceKey', { args: [0, 100] }); // → "Price (0 - 100 EUR)"
```

`args` fills `{0}`, `{1}`, ... exactly as SAPUI5 does.

### A different i18n model

```ts
await Ui5I18n.getText(page, 'someKey', { modelName: 'appI18n' });
```

Defaults to the conventional `'i18n'` model, then falls back to scanning _any_ model that looks
like a resource bundle - so an app that names its model something unusual still works without you
having to know that up front. [`Ui5Model.listModels()`](model-data.md#which-models-does-this-app-have)
shows what's actually there if a lookup surprises you.

## Missing keys throw

```
[playwright-sapui5] Ui5I18n.getText: no i18n text found for key "noSuchKey". Check the key's
spelling, or pass { modelName } if this app's resource bundle isn't on the usual "i18n" model ...
```

This is deliberate. SAPUI5's own `getText()` returns **the key itself** when there's no such text,
so a typo'd key would otherwise sail through and surface much later as a baffling assertion
failure against the literal string `"noSuchKey"`. Failing at the lookup points straight at the
real problem.

Use `hasText()` when a key's existence is itself what you're checking:

```ts
if (await Ui5I18n.hasText(page, 'optionalFeatureLabel')) {
  // only some deployments translate this
}
```

## What this doesn't do

It doesn't change the app's language. To test a specific locale, start the app in it - SAPUI5
accepts an `sap-language` / `sap-ui-language` URL parameter - and then these lookups return that
locale's strings automatically, with no test changes at all. That combination is the whole point:
one test, every language.
